{# The remote file explorer. One card, because it is one thing: a folder, and what you can do to what is in it. There is no toolbar. Every verb is on the right-click menu at the bottom of this file, because every verb acts on rows and that is where the rows are -- a toolbar above a scrolling list puts a scroll between the Delete button and the thing it deletes. What stays up here is navigation: Up, the path, Go, Refresh. Those act on the view, and a folder that is empty or refused has no row to right-click. Note there is no capability gate anywhere in here. Unlike the Firmware and Network panels -- whose read halves are inventory and whose write halves need `issue_commands` -- every route behind this panel needs `issue_commands`, browsing included. tools.html does not render the tab at all without it, so a gate here would be a second, quieter copy of a decision already made. See hub/files_web.py for why browsing is on that side of the line. #}

{# The action menu. Every verb in this panel lives here and nowhere else: they act on the rows, so they are on the rows, which is the answer a right-click has meant in every file manager since before this product existed. The location bar keeps Up, Go and Refresh because those act on the VIEW -- and because an empty or refused folder has no row to right-click. Not page-level, unlike the dialogs. A dialog must outlive the tab being switched away (see _tool_files_dialogs.html); a menu must NOT, and `position: fixed` inside a panel that gets display:none does exactly that on its own. Every entry is always here, disabled when it does not apply, never omitted. A menu with three entries on one row and eight on another teaches an operator nothing about what this panel can do -- and "Paste is grey because nothing is on the clipboard" is an answer to the question the right-click asked. Same reasoning as the process menu on the machine page, whose look these rules are a copy of. #}
