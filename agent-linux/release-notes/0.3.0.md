The first Linux agent that can update itself, plus live command output, available-update reporting, a process list, and a fix for a machine going quiet behind a dead network share.

**Every Linux machine already running the agent needs this installed by hand, once.** 0.1.0 and 0.2.0 have no self-updater at all, so nothing will deliver 0.3.0 to them. Re-run the installer on each box:

```sh
curl -fsSL https://raw.githubusercontent.com/aw08-2004/Temp_Monitor/linux-agent-v0.3.0/agent-linux/install/install.sh | sudo bash
```

The URL names the release tag rather than `main`, so the script you run as root is the one that shipped with this release, not whatever `main` holds on the day.

**Know what this step trusts.** The installer downloads the agent over HTTPS from this repository's GitHub releases and checks only that it is a Linux executable. It does **not** check the build against the fleet's signing key, which every self-update from 0.3.0 onward does. So this one-time step trusts GitHub and TLS, exactly like a first install. If that is not acceptable for a machine, build the agent yourself and install it with `--binary` instead.

No secret is needed the second time. The installer keeps the machine's existing enrollment secret, its identity (so it stays the same entry on the console, with its history) and any hub address it was pointed at. From 0.3.0 on, updates arrive on their own like the Windows agent's, within about fifteen minutes of a release.

**Deploy the hub first.** Use hub 1.133.0 or later. The process list needs it; everything else works against hub 1.123.0.

## It updates itself now

A 0.3.0 machine checks every fifteen minutes for a newer Linux build and installs it. The update is signed with the same offline key as the Windows agent's and is checked before anything is written. A download that does not match what the signed manifest says it should be is refused. The hub cannot point a machine at a build of its own choosing.

The previous build is kept until the new one has actually reached the hub, so a release that starts but cannot connect does not strand the machine.

It only ever takes a Linux build. The Windows agent's releases are a separate train, and the hub now tells a Linux machine only about Linux ones.

To hold one machine at its current build, set `FLEETHUB_NO_UPDATE=1` in `/etc/fleethub/agent.env` and restart the service.

## What you will notice on the console

- **Script output appears while it runs.** A `run_script` on a Linux box used to show nothing until it finished. It now streams to the terminal as it goes, like a Windows PC.
- **Available updates.** The Patches page lists what `apt` or `dnf` says is waiting on each Linux machine, checked every six hours. Security updates are marked where the package manager says so, and anything it does not classify says "unknown" rather than guessing. **It reports only.** Nothing installs an update on Linux yet, and the console will not offer to.
- **The Processes card works.** Open it on a Linux machine's page and the list appears within a few seconds. It shows CPU as a share of the whole machine (the same meaning as on a PC), memory, owner, the program's path and the systemd service it belongs to. It samples only while somebody has the card open. **Listing only:** there is no End task or Restart on Linux yet, and the right-click menu does not appear.
- **The console knows what a Linux machine can do.** The agent now reports which commands it supports. The hub stops offering, and refuses to queue, anything else, instead of sending a command that fails on arrival.

## A dead network share no longer silences a machine

If an NFS or CIFS server went away, the old agent could hang for good on the first disk check. The machine then kept answering commands but stopped sending temperatures and disk readings, with nothing in any log to say why.

The agent now reads the mount table without touching network filesystems it would skip anyway. It gives every remaining disk two seconds to answer, and a mount that doesn't answer is simply left out of that report.

## If it misbehaves

- **Check the version.** The machine page should read 0.3.0.
- **Read the log.** `journalctl -u fleethub-agent` has what the agent logged. A failed update check says so there at Debug level, so raise the level if a machine never seems to update.
- **Update not arriving.** A machine that stays on 0.3.0 after 0.4.0 is released most likely can't reach GitHub. Run the installer again to update it by hand.
- **Processes card stuck.** If it says "Waiting for this machine to report its processes" for more than half a minute, the machine is not on 0.3.0 yet, or the hub is older than 1.133.0.
