Four new capabilities and a handful of fixes. The biggest one is the feature this product has needed since the day backups existed: if a machine locks you out with BitLocker, the hub now has the key. The other three answer long-standing "why can't I" questions — looking at a subnet, picking which GPU the charts mean, and collecting the event logs that matter without collecting everything else.

**Deploy the hub first, as always.** This release needs hub 1.120.0 for BitLocker escrow and 1.118.0 for event logs. If you skip to the agent first the new features silently do nothing — the agent talks about capabilities the hub does not recognise, and the hub ignores what it does not understand. No damage, just no result.

## BitLocker key escrow

A machine that BitLocks you out — forgotten PIN, TPM cleared, motherboard swap — has always meant a site visit or a wipe. The recovery key is sitting in Entra or AD, but getting at it mid-boot means authenticating to a cloud tenant from a machine that will not let you past the pre-boot screen, which is the one moment in the lifecycle where that is hardest.

The agent now asks the OS for every recovery protector on every fixed drive and sends the keys to the hub. They are encrypted in transit (HTTPS or loopback only — the agent refuses an HTTP escrow URL on a routable address) and at rest with the same key the hub uses for backup archives. A machine page that has keys shows a BitLocker tab; a machine that has none shows nothing, because a tab that says "no keys" on a machine that is not encrypted is a tab that makes you worry about the wrong thing.

Nothing is sent until the hub acknowledges the capability. An agent running against a hub that predates 1.120.0 holds the keys locally and waits; they arrive the next time the hub is updated, because the posture is rechecked on every heartbeat, not only on the reading that generated it. An agent that cannot reach the escrow endpoint — firewall, DNS, certificate mismatch — retries every heartbeat and logs the reason, so `companion.log` tells you what is wrong rather than merely that something is.

The hub stores only the latest keys per machine. A drive re-encrypted with a new protector replaces the old one, because the old key is no longer the one you need. A drive that is decrypted has its entry removed, because holding a key for a lock that is not there is an invitation to trust it.

**What you will notice.** Nothing, on a healthy fleet. The first keys arrive with the first agent update and show up on the machine page. A locked-out machine is recoverable from the hub without leaving your chair. If the BitLocker tab never appears on a machine you know is encrypted, check `companion.log` — the agent says whether it found protectors, whether the hub accepted them, and whether the transport refused.

## Network discovery

The question this answers is the one that starts every shadow-IT audit: what is on that subnet that the hub has never heard of?

The sweep runs on a machine that is already there, not from the hub — the same relay reasoning the wake feature uses to reach a sleeping PC. An ARP probe, not a ping. A Windows PC at default firewall settings does not answer ICMP from an unknown host, so a ping sweep of an office subnet finds the printers and misses the PCs, which is the exact inverse of what a shadow-IT hunt is for. Nothing on a segment can decline to answer ARP and stay reachable, so ARP is the one probe whose silence really means nothing is there.

An operator picks a subnet from a list — the machine's own subnets, from the NIC inventory — rather than typing one. ARP does not cross a router, so this is a statement of fact before it is a rule, and it is also the answer to the worry that a discovery sweep is a scanner pointed at a colleague's network. There is no way to aim one. There is no schedule, no configured range, and no fleet-wide sweep button, and each of those absences has a recorded reason.

The verdict on each address is computed when the list is read, against the fleet as it stands then, not written at ingest. A machine enrolled an hour after a sweep turns that scan's unknown device into itself; a machine deleted from the fleet turns back into a finding. One stale false alarm is what stops a shadow-IT list being read at all.

A discovered device becomes nothing. No enrollment, no naming, no alert, no command. The classification is a MAC match, and a MAC is a claim a device makes about itself, so acting on one automatically would let anything on the segment decide what the fleet does about it.

**What you will notice.** A new Network tool on machines that are old enough to have the NIC inventory (which is what the sweep reuses). Pick a subnet, run a sweep, get a list. The hub version does not matter for this one — the agent does all the work and the hub stores the result.

## Configurable sampling, retention, and sensor picks

Three settings that were the hub's decision and are now yours:

**Sampling cadence.** The agent reported temperatures every five seconds and everything else every ten. A fleet on a metered link had no way to report less often; a site that wanted finer charts had no way to ask for more. Both numbers now ride the config channel. Neither touches liveness — the heartbeat is its own loop — and neither touches a machine somebody has open, which stays at 1 Hz because that cadence exists to make a three-second spike visible. An agent that predates the keys ignores them and keeps its compiled 5/10, so nothing breaks while the fleet catches up.

**Per-metric retention.** Retention was one window for every metric. Per-second network and disk-I/O numbers are the ones that make the readings table grow and the ones nobody wants a year of, but shortening the fleet-wide window to suit them throws away the temperature history that is the reason the table exists. Each collection toggle now has a retention window beside it, and the prune blanks that metric's columns rather than deleting the row — a reading is shared by temperature and twelve optional columns, so "keep network for a week" can only mean NULLing the network fields. That NULL is already what a toggled-off metric stores, so the charts, the bucketing and the history endpoint read it unchanged. A metric aged out and a metric never collected look the same downstream, which is honest in both cases. Zero means "follow the fleet-wide window" and is the default for all eight, so an untouched hub prunes exactly as it did.

**Sensor picks.** The GPU, disk and network sensors were hardcoded: first Used Space sensor in the block (an arbitrary drive on a four-drive workstation) and busiest adapter (the virtual switch on any box running Hyper-V bridged onto the office NIC). Both defensible, both wrong, and neither visible on a chart captioned "Disk usage". The picks are now preference lists, like the CPU one. They are hub-side, unlike the CPU one, because the hub re-derives them from the reported sensor block on every read, so they apply to every agent already in the field rather than waiting on a release. Disk and network ship empty, meaning exactly the behaviour that predates them.

**What you will notice.** New settings on the Settings page. If you change nothing, nothing changes. If you shorten network retention to seven days, the next prune NULLs the old network columns and the charts keep working.

## Event log collection

The question this answers is the one Event Viewer can only answer one PC at a time: is somebody brute-forcing that account?

An operator names what matters — a channel, optionally event IDs, levels and a provider — and the agent compiles all of one channel's subscriptions into one Windows event query, so the filtering happens inside the event service and only matches cross the wire. Identical repeats inside five minutes share a row with a count instead of becoming five hundred rows, which is also the only readable form of the answer. Both the retention window and a per-machine row cap existed before the first row was written, because the case that fills a disk does it in an afternoon and the prune runs daily.

The empty report is the part that is easy to leave out and expensive to miss. A healthy machine sends an empty list on every pass, and storing that is what separates "your fleet is quiet" from "your collector stopped" — the failure every log console gets wrong. The same reasoning runs the other way for the subscription document: an empty one is still sent, because deleting the last subscription has to be able to stop collection rather than read as silence.

Reading events is view plus machine scope, like a machine's disks or its available updates. Deciding what the fleet collects is manage_settings — a subscription names no machine and issues nothing, so a new capability would only have shipped switched off for everybody.

**What you will notice.** A new Events page on the sidebar. Create a subscription on the Settings page; events start arriving on the next agent report. A machine too old for the event reader fails the command with a message the console renders verbatim, which tells you more than a missing button could.

## Fixes

**A refused restore no longer looks like a slow one.** A restore row was opened before the command was queued and closed only when the agent POSTed a result, so every path that ended without that POST was invisible. The one that bit: the agent asks the hub for the restore plan, the hub refuses, and the executor deliberately reported that against the command and not the restore — so the console showed "running" with no count and no reason for six hours, on machines that had failed within the same second they claimed the command. The hub now closes the restore with its own sentence when it refuses a plan, a second reconciliation pass closes any other dead restore from its command's terminal status ahead of the 24-hour sweep, and `start_restore` checks that the destination still exists rather than merely being set. Two of the three changes are hub-side on purpose so they work against agents already in the field.

**Backup files can be downloaded without a shell on the hub.** `restore_backup.py --extract` already answered "send me that one file without pushing it onto a PC", but only for whoever holds the master key and a shell on the hub. The hub already holds the key and already brokers every upload, so the only new part is a tar walk. The row menu is the Files tab's, opened by the row's own button as well as by a right-click. Streamed end to end because an archive is routinely gigabytes and the hub's disk holds the database everything else depends on.

**The agent project builds again.** Two faults arrived together with event log mining and either one alone stopped `dotnet build` before a single file compiled. An XML comment used the repo's own dash style inside a `<comment>` element, and XML comments may not contain `--`, so the project file failed to parse with MSB4025 and no hint about the real complaint. System.Diagnostics.EventLog was pinned to 10.0.0 to match System.Management, but ServiceController is on 10.0.6 and depends on this same package at that version, so the pin was a downgrade and restore refused it. Both fixed; the whole agent compiles on Linux under EnableWindowsTargeting.

## The usual

**What you need to do: nothing.** It arrives the way every agent update does, within about fifteen minutes.

**Installing an agent update restarts the service**, which drops any remote session or terminal open at that moment. Reconnect and it behaves normally.

**If it misbehaves.** Check the version on the machine page: it should read 3.37.0. For BitLocker issues, `companion.log` says whether keys were found, whether the escrow URL was reachable, and what the hub answered. For event log issues, the same log names the subscription, the query, and the count. For restore issues, the restore row itself now says what happened — look there before the log.

**Which hub you need.** Hub 1.120.0 or later for BitLocker escrow. Hub 1.118.0 or later for event log collection. Network discovery, sensor picks and cadence settings need no particular hub version — the hub stores what the agent sends and re-derives what it can. The ordinary rule applies: hub first, then let the agent arrive on its own.
