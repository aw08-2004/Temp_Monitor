Two changes. The agent now reports which operating system each machine is running, and a
script run by a **rule** gets a clean shell every time.

## The console can finally tell you what your fleet runs

**What was missing.** The console knew a PC's manufacturer, model, serial and service tag,
and nothing at all about what it was running. "How many are still on Windows 10?" — the
question that decides a refresh budget — had no answer anywhere in the app.

**What changed.** Every report now carries the operating system's name, version, build number
and architecture, read once at startup from Windows itself. The hub turns that into an **OS
column on Asset Inventory** (searchable and sortable — type `windows 10` and you get exactly
those machines), an **OS line on each machine's page** with its build number, and an
**operating-system breakdown on the Dashboard**.

**Windows 11 machines that call themselves Windows 10 are counted correctly.** Microsoft
shipped 11 as build 22000 of the same product and never changed the name Windows reports, so
plenty of genuine Windows 11 machines describe themselves as "Windows 10". The hub decides
from the build number rather than the name, which is why the Dashboard's count is right even
where the machine's own wording is not. The machine page shows you both, so you can see it.

**Machines fill in as they update, not all at once.** An agent reaches every machine within
about fifteen minutes, and until a given machine has updated the hub falls back to whatever
Active Directory recorded for it — coarser, no build number, and as fresh as the last
directory sync. Where the hub is quoting AD rather than the machine it says so, on hover. On
a hub with no directory sync those machines read "--" until their agent lands.

**Nothing is sent that was not already visible.** This is the same class of inventory as the
model and the serial number: read once at startup, sent alongside them on the ordinary report.

**Needs hub 1.86.0 or later** for the columns to exist. An older hub ignores the new fields
entirely, so an agent that updates first simply has nothing to show yet — update the hub and
the machines fill in on their next report.

## A rule's script starts from a clean shell every time

Nothing here changes for scripts you run yourself from the Terminal tab.

**What was wrong.** The agent keeps one long-lived PowerShell (or cmd) per operator, on
purpose: when you type at the Terminal tab, your `cd` is still there on the next command, your
variables are still set, and that is what makes it feel like a real terminal on the box. The
shell is keyed on whoever issued the command.

A rule is issued as `rule:<id>`, so every rule got a shell too — and kept it. Every firing of
that rule on that machine landed in the **same** PowerShell process, reused for as long as the
session stayed warm, still carrying the previous firing's working directory, its variables and
any modules it had imported.

That makes a rule's script not reproducible from its own text. A script that changes directory
quietly changes what the *next* firing's relative paths mean. One that sets a variable leaves it
set. A script that works when you test it can behave differently at 3am on its fortieth run, and
nobody is watching to notice.

**What changed.** A script run by a rule now gets a **fresh shell every time** — the session is
discarded once the submission finishes. Every firing starts from the same state. Scripts you run
by hand are untouched and still persist between commands, because there the persistence is the
point.

**If you wrote a rule script that relied on state left behind by its previous run**, it will
stop working — and it was already unreliable, because the shell could be reaped at any time by
the idle timer. Make such a script set up whatever it needs at the top.

**Costs one process start per firing.** On a rule that fires every few minutes at worst, that is
not measurable.

**Pairs with hub 1.81.0**, which adds the Scripts library and gives every rule command a real
parameter editor. The agent change stands on its own, but the two were written together.

## Both changes

**What you need to do: nothing.** It arrives the way every agent update does, within about
fifteen minutes.

**One thing to expect.** Installing an agent update restarts the service, which drops any remote
session open at that moment. Reconnect and it behaves normally. Telemetry, commands and the
machine page reconnect on their own.
