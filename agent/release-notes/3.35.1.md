One fix, no new features, and no hub update needed. If your fleet is mostly Dell, this is the
release where the Firmware tab starts working.

## Dell machines can now read their firmware settings

**What was wrong.** Almost every Dell in the fleet showed a red error on its Firmware tab —
*could not read: the firmware interface returned no settings* — and had done since the feature
shipped. HP and Lenovo were unaffected.

The agent was reading Dell's settings from the interface that **Dell Command | Monitor**
installs. On a Dell that has never had Command | Monitor on it — which is a Dell as it comes
out of the box, and therefore most of a normal fleet — that interface is not there.

What made it look like a fault rather than a missing component is that Dell leaves the empty
shell of it behind. The agent checked for the shell, found it, concluded the machine was
manageable, then asked it for settings and got nothing back. An empty answer from an interface
that is present is a genuine fault, so that is what it reported — correctly, about the wrong
interface.

**What changed.** The agent now reads the interface that ships on a stock Dell business image,
and falls back to Command | Monitor for the machines that do have it. Both are tried, so
nothing that worked before stops working.

**What you will notice.** Dells that showed an error now list their settings — typically a few
hundred of them, searchable, with the machine's own names for them. The line above the table
names a different interface than it used to; that line now tells you which one actually
answered, which is the one to mention if you ever have to chase this.

**A Dell that still reports nothing is now telling you something real.** Before this release
that error was the default state and meant nothing. Now it means the machine genuinely has no
Dell firmware interface, or has one that is failing, and the message names which was tried.

**Changing a Dell setting was broken in the same way and is fixed with it.** Applying a change
from the Firmware tab aimed at the same absent interface, so it would have failed on exactly
the machines that could not be read. Since those machines never showed a settings table, you
are unlikely to have hit it.

**How far this goes, honestly.** Reading has been checked against real Dell hardware. Writing
has not — the change is built from Dell's own published interface definition, but no setting
has actually been written through the new path yet. **Before you use this on a fleet, change one
setting on one machine and confirm it took.** The tab verifies by re-reading the setting
afterwards, so it will tell you truthfully whether it landed; that is worth doing deliberately
once rather than discovering it during a rollout.

**Machines with a BIOS setup password.** The password is sent in a different form through the
new interface than through the old one. If you have setup passwords deployed, the single test
change above is worth doing on a machine that has one.

## The usual

**What you need to do: nothing.** It arrives the way every agent update does, within about
fifteen minutes.

**No hub update is needed.** Nothing here depends on a hub change, and the shape of what the
agent sends is unchanged — the same report, now with something in it. Any hub version that runs
3.35.0 runs this.

**HP and Lenovo are untouched.** No change to how either is read or written.

**Firmware is re-read every six hours, not on every heartbeat**, so a machine may take that long
to correct itself after the update. **Re-read** on the machine's Firmware tab does it now.

**Installing an agent update restarts the service**, which drops any remote session or terminal
open at that moment. Reconnect and it behaves normally.

**If it misbehaves.** Check the version on the machine page: it should read 3.35.1. A Dell still
showing an error after a Re-read is worth reading the message on — it now names the interface
that failed, and *access denied* there means something on that machine is blocking the agent
rather than the setting being unreadable. A virtual machine reporting *no manageable firmware*
is correct and always was; that is the quiet, permanent state for hardware with no BIOS to
manage, and it is not an error.
