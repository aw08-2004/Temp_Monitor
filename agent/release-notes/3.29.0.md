The agent can now put a message on a user's screen and answer questions about a machine that
telemetry does not cover. Both are driven by rules you write on the hub, so nothing changes
until you write one.

**The agent can ask the person at the PC something.** Until now the only window this software
ever put in front of an end user was the remote-support consent prompt. A rule can now show a
dialog — a title, a message, and up to four buttons — and what the person clicks decides what
happens next: *"Your PC has been running for 9 days. Restart now?"* with **Yes**, **No** and
**Later**, where Yes restarts, Later asks again in four hours, and No is recorded and does
nothing. The message text can quote the machine's own values, so it can say nine days rather
than "a while". Needs hub 1.78.0 or newer, which is where the rules themselves live.

**The agent never decides what a button means.** It is told button IDs, it reports back which
one was pressed, and the hub maps that to an action. This is deliberate: it means you can
change what "Later" does, or add a follow-up action, without waiting for a new agent to reach
every machine. It also means the agent cannot be talked into restarting a PC by a malformed
message — the restart is a separate command the hub issues afterwards, through the same
permission checks and audit trail as one you issue by hand.

**Nobody signed in is an answer, not a failure.** A message sent to a PC sitting logged-out,
or at the lock screen, reports "nobody was signed in" and does nothing. Your rule decides
what happens then — normally, ask again in half an hour. This is why a rule does not quietly
fail on the third of your fleet that is switched on and unattended, and why nobody arriving
on Monday is greeted by a stack of prompts about Friday.

**The agent can also be asked to go and look something up.** Rules can now read a registry
value, check whether a file exists, read a file's version, or run a WMI query, and use the
answer in a condition — "every PC where Chrome is older than 120", say. Four of the five
kinds only read. The fifth runs a PowerShell script you write, and it is switched **off** on
the hub by default: a script probe is arbitrary code running on a schedule on every PC a rule
looks at, and turning that on should be a decision rather than something inherited.

**What you need to do: nothing.** It arrives the way every agent update does, within about
fifteen minutes. A machine on this version with no rules pointed at it behaves exactly as it
did on 3.28.1 — the new code only runs when the hub asks it to.

**Two things to expect.**

Installing an agent update restarts the service. If a message happens to be on somebody's
screen at that moment, the prompt stays up but their answer is no longer being listened for,
so it is not recorded and the rule asks again on its next pass. Rare, and it costs one
duplicate prompt.

If the styled dialog cannot be drawn — an unusual desktop, a graphics failure — the agent
falls back to a plain Windows message box, which can only carry two buttons. A three-button
message degrades to the first two on that machine, so a "Later" option can be missing there.
The fallback is rare; it exists so a message still reaches someone rather than silently not
appearing.

**If it misbehaves.** The version on the machine page should read 3.29.0. A message that
never appeared is worth checking against the rule's own history on the hub, which records the
outcome for every machine it was sent to — "nobody was signed in" and "could not be shown"
are recorded separately, and they mean different things. The dialog itself runs as a
short-lived separate process in the user's session, the same technique remote control uses,
so a machine where messages never appear but everything else works is usually one where that
injection is being blocked rather than one with a rule problem. Its working files live under
`%ProgramData%\FleetHub\Agent\messages` and are cleaned up after each message.
