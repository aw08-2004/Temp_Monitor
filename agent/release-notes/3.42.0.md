Remote view no longer dies when the TURN relay is down. If a direct connection cannot be made, the session now moves onto the hub and keeps going. Event log rules also stop trusting two kinds of count they could not vouch for.

This is a minor rather than a patch because the console offers something new for it (the hub relay), and the agent sends the hub new details with every event log report.

**Deploy the hub first, as always.** This needs hub 1.141.0. On an older hub the agent behaves exactly as before: the console never asks it to relay, and the hub ignores the extra event detail.

## Remote view falls back to the hub

Until now, a remote session needed WebRTC to find a path: directly, or through the TURN relay. When the relay was down or unreachable, every session ended with *Connection failed*, even though the browser and the PC were both talking to the hub at the time.

Now, if the connection fails, or has not connected twenty seconds after the PC answers, the viewer asks the hub to carry the session:

- The agent sends its video to the hub over the same HTTPS connection it reports on, and the browser fetches it from there. Mouse and keyboard go the other way.
- The status pill reads **Live (via hub)** instead of **Live**. Everything else works the same: input, Ctrl+Alt+Del, the lock screen, fullscreen and the quality settings.
- **It is slower.** Every frame passes through the hub, so expect a little more delay and some extra hub bandwidth. Lower the quality preset if the picture lags.
- **The hub sees the picture.** Through the TURN relay the video is encrypted end to end. Through the hub it is encrypted only as far as the hub. So each switch writes a `remote_session_relay` row to the audit log, and nothing is stored. Frames are held in the hub's memory for a few seconds.

**To turn it off**, switch off *Fall back to relaying through the hub* under Settings → Remote Control. A session that cannot connect directly then fails as before.

It is a fallback, not a fix: a TURN relay that is down is still worth repairing, and the usual diagnosis applies. `remote-helper.log` on the PC now also says when and why a session switched.

A PC borrowed from another hub is never relayed.

One more change you might notice: when the connection drops, the agent now keeps the session open for up to 45 seconds instead of ending it at once. That gives the viewer time to switch, and lets a connection that recovers on its own carry on.

## Event log rules wait until a count is real

Two cases where an `event.*` rule could read a confident zero off a PC that was not actually watching:

- **A new subscription.** For one heartbeat after you add one, the PC's report could still come from its old subscription list, and the new event id read 0. Each report now says which list it was collected under, and the count stays empty until that list includes the id.
- **After a collector error clears.** One clean report used to make every count trustworthy again, even though the counting window still covered the time the PC could not read the log. The counts now stay empty until that time has left the window (a day, by default).

An empty count does not trigger a rule, which is the point: a rule should never fire, or stay quiet, on a number nobody measured.

## The usual

**What you need to do:** nothing, beyond deploying hub 1.141.0 first. It arrives the way every agent update does, within about fifteen minutes.

**Installing an agent update restarts the service**, which drops any remote session or terminal open at that moment. Reconnect and it behaves normally.

**If it misbehaves.**

- **Check the agent version first.** The machine page should read 3.42.0. An older agent never offers the relay.
- **The session fails instead of switching.** Check that *Fall back to relaying through the hub* is on, and that the browser is current. The relay needs WebCodecs, which recent Chrome, Edge and Firefox have. If either is missing, the failure message says so.
- **It switched, but the picture stays black.** Report it with the machine name and `remote-helper.log`. The log says whether frames reached the hub (*first upload accepted*) and how many were dropped.
- **It switches when TURN is healthy.** It should only switch when WebRTC really failed. Read the ICE summary in the viewer before the switch, and the coturn log, as before.

**Which hub you need.** Hub 1.141.0 or later. The ordinary rule applies: hub first, then let the agent arrive on its own.
