A security update. Nothing changes on screen.

**What was wrong.** The agent keeps its working files in `%ProgramData%\FleetHub\Agent` —
its identity, its config, and the staging folders it downloads into. Nothing ever set
permissions on that folder, so it inherited them from `C:\ProgramData`, and that default is
not what it looks like. Alongside the expected read-only grant, `C:\ProgramData` hands every
folder beneath it this:

    BUILTIN\Users:(CI)(WD,AD,WEA,WA)

That is *create files and create folders*, inherited by every subfolder. Files the agent had
already written were safe — an ordinary user could read those but not change them — but any
user signed in to the machine could **drop a new file** into any of the agent's staging
folders, and would own whatever they dropped.

**What it could have done.** Taken over the machine. The self-updater stages the next agent
binary at `update\TempMonitorAgent-<version>.exe`, and the version in that filename comes
from a manifest published openly on GitHub — so the path was predictable. A standard user
could create that exact file ahead of time, keep ownership of it through the agent's own
write, and replace the verified bytes in the moment between the download being checked and
the file being swapped into place. The service then restarts into that file, as SYSTEM.

That is a local privilege escalation: it needed an account on the machine already, and it
could not be done from the network or from the hub. But it turned any ordinary user account
into full control of the machine, which is the whole boundary the agent is supposed to keep.

**Nothing suggests this was used.** It is being fixed as a real exposure, not a theoretical
one, because the agent runs on every machine in the fleet and runs as SYSTEM.

**Two fixes, not one.** The folder's permissions are now set explicitly, at every service
start, to SYSTEM and Administrators only — ordinary users keep read access so support can
still open the log, and lose the ability to write anything. Every process that legitimately
writes there already runs as SYSTEM, including the remote-support helper, so nothing loses
access it was using.

Separately, the self-updater now re-checks the staged file's hash from disk in the instant
before it swaps it in, rather than trusting the check it did on the downloaded bytes a moment
earlier. The permissions fix removes the opening; this makes the update path not depend on
permissions being right in the first place.

**What you need to do: nothing.** It arrives the way every agent update does, within about
fifteen minutes. The permissions are repaired on the machine as the updated agent starts, so
machines already deployed are fixed by the update itself — there is no need to re-run the
installer anywhere.

**One thing to expect.** Installing an agent update restarts the service, which drops any
remote session open at that moment. Reconnect and it behaves normally. Telemetry, commands
and the machine page reconnect on their own.

**A note for anyone who has looked in that folder.** If someone had already planted a file
there before this update, the new permissions do not remove it — they only stop new ones
arriving. On a machine you have reason to worry about, look for unexpected files under
`%ProgramData%\FleetHub\Agent` (and the older `%ProgramData%\TempMonitorAgent`), in
particular anything in `update\` that is not the version you are running.
