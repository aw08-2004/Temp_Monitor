One fix, no new features. It is a fix to something that has never worked, rather than
something that broke recently: a PC you delete from the console can now be enrolled again.

**Deploy the hub first, as always**, though this is a gentler case than most — see *Which hub
you need* below.

## A deleted machine can be enrolled again

**What was wrong.** Delete a machine from the console, then reinstall the agent on that PC with
the correct enrollment secret, and the console kept reading **Online, not enrolled**. Not for a
while — permanently. Its temperature kept updating the whole time, so it looked like a healthy
machine with a puzzling badge, and there was nothing in any log on either side to say
otherwise. Uninstalling and reinstalling again changed nothing, because the thing that needed
to go was never in the install directory.

Every command, terminal session, package deployment, backup and process report on that machine
silently did nothing, which is the state the *not enrolled* badge exists to warn you about. The
badge was right. There was just no way out of it.

**Why.** The agent's enrollment identity is a small file under `%ProgramData%`, deliberately
kept out of the install directory so that logs survive an upgrade. Deleting a machine on the
hub removes its end of that pairing. The agent went on presenting a credential for something
that no longer existed, was refused every ten seconds, and had no way to tell "you have been
deleted" from "the network is having a bad minute" — so it kept the dead credential and carried
on. A fresh install found that file, concluded it was already enrolled, and never asked.

The telemetry kept flowing throughout because that path is deliberately unauthenticated. That
is what made this invisible rather than obvious.

**What changed.** The hub now says *why* it refused, and the agent acts on it. Told that the hub
has no record of it, the agent throws its local enrollment away and enrolls again from scratch —
within a heartbeat or two, with no intervention. Told it has been **revoked**, it keeps the
identity and stays down, which is the point of revoking it.

**The uninstaller now removes the enrollment file too**, and still leaves the logs. So *uninstall,
then reinstall* does what everyone already assumed it did. That half works against any hub
version, including one you have not updated yet.

## What you will notice

**Deleting a machine that is still running now really does mean "start over".** The console has
always described Delete this way — *if the machine's agent is still running it will re-enroll
and reappear on its next report* — and that is now true. Before this release such a machine
came back as a half-thing: visible, reporting temperatures, permanently unmanageable.

**So Delete is still for machines that are actually gone.** That has not changed, and it is
worth saying plainly: deleting a decommissioned-but-still-powered-on PC does not make it go
away. It comes back within about ten seconds, now as a fully enrolled machine with a clean
history rather than as a stuck one. **If you want a machine gone, uninstall the agent first,
then delete it.** In that order it stays gone.

**A machine you have already lost this way fixes itself** once both halves are in place. There
is nothing to run on it and nothing to visit it for.

**Nothing changes for a machine that is enrolled and working**, which is all of them. A healthy
agent is never refused, so none of this code runs.

## Which hub you need

**Hub 1.112.0 or later** is what this pairs with — 1.112.0 is where the hub half landed, and
every hub since carries it. The ordinary rule applies: hub first, then let the agent arrive on
its own.

**This release is unusual in that an older hub does not break it.** A hub below 1.112.0 cannot
say why it refused, and the agent treats an unexplained refusal as "enroll again" — which is the
right answer for the case in this note. What an older hub cannot express is the *other* case, a
deliberately revoked agent, so on an old hub a revoked agent would re-enroll instead of staying
down. Revoking an agent is not something the console offers today, so this is a gap on paper
rather than one you can reach; updating the hub closes it regardless.

## The usual

**What you need to do: nothing.** It arrives the way every agent update does, within about
fifteen minutes.

**Installing an agent update restarts the service**, which drops any remote session or terminal
open at that moment. Reconnect and it behaves normally.

**If it misbehaves.** Check the version on the machine page: it should read 3.36.0. A machine
still reading *not enrolled* an hour after both halves are deployed is worth looking at
`companion.log` on — the agent now says, in as many words, either that the hub does not
recognise it and it is enrolling again, or that no enrollment secret is available. The second
means the secret is missing from that machine's registry and the installer needs re-running;
that has always been possible and was previously just as quiet as the bug above.

**A machine that reports temperatures but never enrolls is still a real state**, and still means
what it always did: the agent has telemetry but no credential. It is no longer something this
fix can leave you stuck in.
