Everything in 3.37.0, plus the one feature that was still missing from it: a service that stops is now put back by the machine itself, without waiting on the hub to notice.

This is a patch number rather than a minor because nothing else changed. If you have not yet read the 3.37.0 notes -- BitLocker escrow, network discovery, the new settings, event log collection -- they still apply, and this release carries all of it.

**Deploy the hub first, as always.** Watchdogs need hub 1.127.0. An agent on 3.37.1 talking to an older hub simply never receives a watchdog, which is the intended outcome rather than a failure: no watchdogs exist to send yet, and nothing on the machine changes.

## Self-healing watchdogs

The case this answers is the one that wakes somebody up: the print spooler stops at 02:00 on the machine that runs the label printer, and nobody finds out until the first shift tries to print.

Restarting a stopped service is something the fleet could already do -- an operator could push `restart_process` from the console. What it could not do is notice. A rule is evaluated on the hub, against data the machine reported on its last pass, which is both too slow for "put this back within two minutes" and useless in the case that matters most: a machine that has stopped talking to the hub is exactly the machine whose services most need someone watching them.

So the machine watches its own. An operator names a service and the machines it should run on; from then on each agent checks every thirty seconds and starts the service if it has been stopped longer than the grace period. The hub is not consulted and does not need to be reachable.

**The grace period exists because a stopped service is usually nothing.** Services stop during their own updates, during a reboot, and during anything an installer does. Sixty seconds by default, and it measures the current outage rather than the time since the last one, so a service that stops, gets restarted, and stops again an hour later gets a fresh minute rather than being pounced on.

**The restart budget is what stops a watchdog making things worse.** Three restarts in an hour by default. A service that will not stay up is not helped by being started a thousand times, and the machine doing that quietly is worse than the machine being down loudly -- so after the budget is spent the watchdog stops trying and raises an alert on the console instead. It also clears itself: once those attempts age out of the window the watchdog resumes on its own, so a bad afternoon does not leave you with something to re-arm by hand the next morning.

**Some services cannot be watched at all.** RPC, DCOM, Plug and Play, WMI, the group policy client and a handful of others are refused when you try to save the watchdog, not silently ignored later. Restarting those does not recover a machine, it finishes it off. The agent itself is on that list too, for the obvious reason.

**Creating one needs both the rule-authoring and the command-issuing permission.** A watchdog is a service restart that runs unattended on every machine it targets, so it is gated like a command rather than like a rule. Somebody who may write rules but may not push commands can read the page and not change it.

**The one thing to know about deleting one.** The machine holds its watchdogs until the hub tells it otherwise, which is what makes them work while the hub is unreachable. The cost of that is the mirror image: deleting a watchdog does not disarm a machine that is offline at the time. It stops on that machine's next heartbeat.

**Start with one machine and one service.** This is the feature's first release and the first time it runs against a real SCM rather than a test double. Point a watchdog at one service on one PC, stop that service by hand, and watch it come back on the machine page before you target a site.

**What you will notice.** A new Watchdogs page on the sidebar, and nothing else until you create one. A watchdog that has restarted something shows it there, per machine, with the history; one that has given up shows on the alerts page like any other alert.

## The usual

**What you need to do: nothing.** It arrives the way every agent update does, within about fifteen minutes.

**Installing an agent update restarts the service**, which drops any remote session or terminal open at that moment. Reconnect and it behaves normally.

**If it misbehaves.** Check the version on the machine page: it should read 3.37.1. A watchdog doing something you did not expect is switched off from the Watchdogs page with the enable toggle, which reaches the machine on its next heartbeat; deleting it does the same. `companion.log` names the service, what the agent found it doing, and what the restart returned, so a watchdog that reports `failed` rather than `restarted` says there why.

**Which hub you need.** Hub 1.127.0 or later. The ordinary rule applies: hub first, then let the agent arrive on its own.
