Commands start the moment you issue them instead of waiting for the machine to ask.

**A click no longer waits out a poll.** The agent used to ask the hub for work every ten
seconds, so anything you issued sat in the queue until that machine's next ask — on average
five seconds of nothing, and up to ten. It now leaves that request open with the hub, and the
hub answers it the instant a command is queued. A restart, a script, a terminal, a deployment:
the machine starts on it within a round trip of the click.

Nothing about how commands are claimed or reported changed, and delivery is still
at-most-once. The old polling is still underneath as the fallback, and it runs whenever the
push path isn't available. A command is never delivered twice, and never delivered only by
push.

**This needs hub 1.76.0 or newer.** Against an older hub the agent asks for the new behaviour,
is answered the way it always was, and keeps polling on the ten-second cadence. Nothing breaks
and nothing needs configuring; you simply don't get the speedup until the hub is updated. An
agent still on 3.26.0 works fine against the new hub too, so the two halves can land days
apart, in either order.

**The hub decides how many machines get it, and it is a small number by default.** Holding a
request open occupies one of the hub's worker threads for as long as it is held, and every
console tab you leave open already occupies one for its live updates. So the limit is on the
hub's capacity, not on your fleet: **Settings → Fleet → "Push commands to at most"**, which
ships at 8. Machines beyond that limit still receive every command, on the old ten-second
delay — they are slower, never skipped.

Raise that limit only after reinstalling the hub, whose installer now provisions a much larger
thread pool for exactly this. Raising it on a hub that predates that will starve the console
instead.

If something between your agents and the hub — a reverse proxy, a CDN, a firewall doing
idle-connection cleanup — closes requests before the hub is done with them, lower **"Hold a
pushed connection for"** below whatever that timeout is. Setting "Push commands to at most" to
0 turns the whole thing off and returns every machine to polling.

**Two cases deliberately keep polling.** While you are typing at a machine's terminal the
agent goes back to its fast one-second cadence rather than holding: those exchanges are a
burst of tiny round trips, they are already quick, and holding would spend a scarce hub slot
on the one case that doesn't need it. And an agent whose request fails outright — hub
unreachable, an error, a dropped connection — falls back to its normal cadence rather than
reconnecting immediately, so a hub having a bad minute doesn't get hammered by its whole fleet
at once.
