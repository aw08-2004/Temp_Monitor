Four fixes, no new features, and no hub update needed. One of them changes something you are
used to seeing: operator email addresses are gone from the agent's own log files.

## Operator email addresses are no longer written to the agent's logs

**What was wrong.** The agent's log files are deliberately readable by anyone signed in to the
machine — that is on purpose, so support can open `companion.log` on a PC without needing
admin rights on it. Every shell action the agent logged wrote the operator's email address
into that file: opening a terminal, reaping an idle shell, resetting one. `remote-helper.log`
did the same for whoever started a remote session.

So on any managed PC, the person sitting at it could read the email addresses of the IT staff
who had worked on their machine, by opening a file they already had access to. Nothing had to
be exploited.

**What changed.** Those lines now carry a short tag derived from the address instead of the
address itself — `Reaping idle/dead shell for 7dcd3a39`. The tag is stable: the same operator
reads as the same tag on every line, on every machine, and across updates, so a log is still
something you can follow through a sequence of events.

**What you will notice.** Searching a machine's `companion.log` for your own email address now
finds nothing. To go from a tag back to a person, use the hub's audit log — the hub records
every command against the operator who issued it, from the signed-in session, and that has
always been the authoritative record of who did what. The agent log's copy was only ever there
to tell one operator's lines apart from another's, which the tag still does.

**How far this goes, honestly.** The tag is not a secret and is not offered as one. An IT team
is small and its address format predictable, so someone determined, who already had a list of
your staff addresses, could work out which tag belongs to whom. What this stops is the case
that actually happens: someone opening the log and reading addresses straight out of it.

**The consent prompt still names you, and that is deliberate.** When a remote session needs
attended consent, the dialog on the user's screen still shows the operator's real email
address — "*someone@example.com* wants to view and control this computer". Naming the person
asking to watch your screen is the entire point of that prompt. Telling the one person who is
being asked to decide is not the same as leaving it in a file for anyone to read later.

## A remote session that cannot capture the screen now says so

**What was wrong.** This affects the fallback capture path, used where Desktop Duplication is
unavailable — some virtual machines, older RDP sessions. That path asks Windows for the screen
and then never checked whether Windows had actually given it one. When the copy failed, the
agent sent the *previous* picture, or a black one, and reported it as a fresh frame.

Those failures are not exotic: the desktop switching, a UAC prompt coming up, a resolution
change while the copy is in progress. From your chair it looked like a remote session that had
frozen on a stale image or gone black, with nothing in the log to say why, and nothing to
distinguish it from a machine whose screen genuinely was not changing.

**What changed.** A failed capture is now reported as a failure. The session retries, as it
already did for an unchanged screen, so a momentary failure during a desktop switch is
absorbed exactly as before and you will not see it. What is different is a failure that keeps
happening: instead of streaming black indefinitely, the session now reports that it is not
getting frames — which is a message you can act on.

**What you will notice.** Fewer sessions that sit on a frozen or black picture. When one does
fail, it tells you, rather than looking like it is working.

## The attended-consent prompt no longer leaks graphics handles

Small, and invisible until it is not. While the consent dialog was on screen it counted down
once every tenth of a second, and each redraw leaked a Windows graphics handle that was never
given back. A prompt left sitting for its full timeout leaked for the whole of it. Fixed by
releasing them properly; nothing about the prompt looks or behaves differently.

## A shell the agent fails to kill now says so

**What was wrong.** When the agent tears down a terminal session it kills the shell process and
everything under it. If that kill failed, the failure was discarded — the agent carried on as
if the shell were gone. Those shells run as SYSTEM, so a kill that did not take left a SYSTEM
process and its children running on the machine with nothing pointing at them and nothing in
the log.

**What changed.** A failed kill is now logged with the process id. The ordinary case — the shell
having already exited on its own, which is what happens when someone types `exit` — is
recognised as normal and stays quiet, so this does not add noise to a healthy machine.

**What you will notice.** Nothing, normally. If you are ever chasing a stray `powershell.exe` or
`cmd.exe` running as SYSTEM on a machine, `companion.log` will now name it.

## All four

**What you need to do: nothing.** It arrives the way every agent update does, within about
fifteen minutes.

**No hub update is needed.** Nothing here depends on a hub change, and nothing here changes what
the agent sends. Any hub version that runs 3.32.0 runs this.

**One thing to expect.** Installing an agent update restarts the service, which drops any remote
session open at that moment. Reconnect and it behaves normally. Telemetry, commands and the
machine page reconnect on their own.

**If it misbehaves.** Check the version on the machine page: it should read 3.32.1. A remote
session that will not show a picture after this update is worth a look at `remote-helper.log`
on that machine — this release did not change how sessions are set up, only whether a failed
screen copy is reported as one, so a session that now says it is getting no frames was almost
certainly showing you a stale picture before.
