One change, and it only matters to rules that ask a user to restart.

**What was wrong.** When a rule puts a dialog on someone's screen — "your PC has been up 9
days, restart now?" — and they press Yes, the hub sends the machine a `restart` command. That
command ran `shutdown.exe /r /t 60`, with no `/f`. Windows treats that as a *request*: an
application holding unsaved work is allowed to veto it, and it does so silently, after
`shutdown.exe` has already exited successfully. So the agent reported the restart as
scheduled, the hub recorded it as done, the countdown appeared — and the machine never went
down. From the user's chair that is indistinguishable from pressing Yes and nothing
happening, which is exactly how it was reported.

**What changed.** `restart` and `shutdown` now accept a `force` parameter. When it is set the
agent adds `/f`, which closes running applications so they cannot cancel the shutdown.

**It is off by default, and it is per rule.** Forcing closes applications *without saving*, so
it is not something to switch on fleet-wide without meaning to. It is a checkbox in the rules
editor, on the follow-up you attach to a message's answer — so you can force the restart that
a user explicitly agreed to, while leaving an unattended maintenance rule polite. Existing
rules are untouched: a follow-up saved before this release carries no `force`, and behaves
exactly as it did.

**When to use it.** On a restart the user just consented to, forcing is usually right: they
were asked, they said yes, and the countdown is their warning. On a rule that restarts
machines on a schedule without asking anyone, leaving it off is usually right.

**If Yes still does nothing after this update**, the restart is probably not reaching the
machine at all, which is a different problem with the same symptom. Check
**Settings → Rules → "command actions enabled"** on the hub. It ships **off**, and while it is
off a rule evaluates normally but issues no command — including the command a message's answer
routes to. The hub now records a skipped follow-up in the audit log on its own line, and the
rules editor shows a warning banner when a rule you are editing depends on the switch, so this
is visible rather than silent. Hub 1.80.0 or later is needed for both.

**What you need to do: nothing.** It arrives the way every agent update does, within about
fifteen minutes. Nothing changes on any machine until a rule actually sets `force`.

**One thing to expect.** Installing an agent update restarts the service, which drops any
remote session open at that moment. Reconnect and it behaves normally. Telemetry, commands
and the machine page reconnect on their own.
