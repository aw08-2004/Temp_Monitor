Two new capabilities in this one. The first is the one this product has been missing longest:
the hub can now see what every machine is missing, decide what may install, and install it
inside a window you chose. The second lets you put an agent release in front of a few machines
before it reaches the rest.

**This one needs the hub first.** Everything below is answered by the agent but asked by the
hub, so a machine on 3.35.0 talking to a hub below 1.93.0 simply never gets asked and behaves
exactly as it did before — it reports into a hub that ignores it, which costs nothing. Update
the hub, then let the agent arrive on its own.

# Patch management

## What the machine now reports

Every machine tells the hub what it currently has available to install, from two places:
**Windows Update** (the operating system, and drivers offered through it) and **winget**
(applications). The console's new **Patches** page is the fleet-wide view of that.

**It is read on a slow loop, not on the heartbeat.** A Windows Update search contacts your WSUS
server or Microsoft Update and routinely takes tens of seconds; winget refreshes its sources
over the network. Neither belongs anywhere near the ten-second heartbeat, so the scan happens
on its own schedule — roughly every six hours, which is about how often the answer changes —
and the heartbeat merely carries the result. **Only changes travel**, so a settled machine
sends this once and then goes quiet.

**On Windows Server there is no winget, and that is not an error.** Server ships no Store and no
App Installer, so those machines report their operating system updates and nothing else. The
page does not pretend otherwise and no amount of installing something by hand changes it.

**A machine with nothing to install still reports.** That sounds like a detail and is actually
the centre of the whole feature — see below.

## Installing

The hub sends a list of updates and the agent installs them, then restarts if the window's
policy says to.

**An update is never reported as installed because the installer said so.** This is the part
worth reading. A silent installer that exits successfully having done nothing is the normal
failure of this entire problem domain, and Windows Update genuinely reports success for updates
that need a restart before they are installed in any sense you care about. So this agent
reports only that it *staged* what it could — and the hub decides the outcome later, by
watching that machine **stop offering the update**. That is why the empty report above matters:
it is the evidence.

**What you will see on the console** is a machine sitting at "restarting" after a patch run,
sometimes for a long time, and then moving to applied. A machine switched off for the weekend
sits there until Monday. That is correct behaviour and not a stall — the alternative is
reporting an outcome nobody observed. The hub gives up after a day and says it could not
confirm, which is a different answer from "it failed".

**Some installed and some did not is its own result.** Eleven of thirteen is the normal shape
of a patch night, and the console names the two that are still outstanding rather than painting
the machine red.

**A restart gives the person at the PC five minutes** and Windows' own warning, and is
deliberately not forced — nothing is closed out from under an open document. That is longer
than the restart command's usual minute, because this one fires inside a maintenance window
with nobody watching. If the window's policy says not to restart, the updates simply finish at
the machine's next restart, and the console says so.

**An update the machine no longer needs is skipped, not attempted.** The hub works from a
report that may be minutes old, so the agent re-checks against a live scan before installing
anything — asking Windows Update for a patch already applied produces a failure that reads
exactly like a broken patch.

**After any install attempt the machine re-reports immediately** rather than waiting out its
six hours. That report is what closes the run.

## What it will not do

**It does not decide what to install.** Nothing installs that somebody has not approved on the
hub, or named explicitly. An update an administrator has *hidden* on a machine is never
offered — that was a decision somebody made at that PC, and overriding it silently would be
worse than not seeing it.

**A machine pointed at an unreachable WSUS reports the problem, not an empty list.** The same
is true of a Windows Update service disabled by policy, or one mid-way through a servicing
stack update. Those are all ordinary on a real fleet, and none of them makes the machine look
fully patched — which is the wrong direction to fail in.

**One source failing does not cost you the other.** A server with no winget still reports its
operating system updates.

# Release channels

## Why you would want this

An agent release currently reaches every endpoint you have within about fifteen minutes of
being signed. That is usually what you want and it is a bad only option, because it means the
first machines to run a new build are all of them at once.

Now you can pin a handful — the reception PC, a spare laptop, your own desk — to **beta**,
publish there first, watch for a day, and then promote. Everything not pinned carries on
exactly as before.

## How it works

**Set the fleet default in Settings, pin individual machines on their own page.** A machine's
Overview card shows which channel it is on and whether that is a pin or the fleet default.
Most machines will never be pinned.

**Both channels are signed with the same key.** Beta is not a looser trust path: the manifest
is signed by the same offline release key, the download is checked against the same signed
sha256, and a tampered or truncated build is refused on beta exactly as it is on stable. What
differs is only *which file* the agent reads.

**The hub cannot point an agent somewhere new.** It sends a channel *name*, and the agent
already holds both addresses. That is deliberate and worth knowing: the release chain is the
one control that still holds if the hub itself is compromised, and moving a machine between
two destinations it already trusted does not weaken it. A hub that could send a URL would.

## The one thing that will surprise you

**Moving a machine off beta does not roll it back.** It keeps the build it has and stops
updating until stable catches up.

This is not a limitation that was overlooked — it is the same rule that protects every update
here: the agent installs only what is strictly *newer* than what it is running, which is what
stops an old or replayed manifest being installed on a healthy machine. Rolling back would
mean turning that off.

In practice it matters less than it sounds, because a beta that gets promoted becomes stable
at the same version number — at which point the pilot machine is already there and simply has
nothing to do. It matters when you abandon a beta instead of promoting it: that machine sits
on a build nothing else runs until stable passes it.

**The console says so rather than leaving you to notice.** A machine ahead of stable is
labelled on its Overview card with what it is running and what stable is on. A PC that has
quietly stopped updating looks broken; one that says why does not.

## What has not changed

**Nothing, if you do nothing.** Every machine defaults to stable, the fleet default ships as
stable, and no beta exists until somebody publishes one. An untouched fleet updates exactly as
it did before this release.

**The dashboard's "agents outdated" count ignores pinned machines**, so a pilot ring running
ahead of stable does not permanently skew the one number on that page you are meant to act on.

## The usual

**What you need to do: nothing**, beyond updating the hub first. It arrives the way every agent
update does, within about fifteen minutes.

**Installing an agent update restarts the service**, which drops any remote session or terminal
open at that moment. Reconnect and it behaves normally. Telemetry, commands and the machine
page reconnect on their own.

**If your machines are below 3.34.0** they land at 3.35.0 directly and pick up everything in
between on the way.

**If patching misbehaves.** Check the version on the machine page: it should read 3.35.0. A
machine showing no available updates at all, on a hub that shows others reporting, is worth a
look at `companion.log` on that machine — the agent records why a scan came back empty, and the
reason it gives is the one the Patches page shows you. A patch run stuck at "restarting" past a
day has not been forgotten; the hub closes it out and says it could not confirm the install,
which is your cue to look at that machine rather than to re-run the whole window.

**If a channel misbehaves.** A machine you pinned to beta that is not moving is usually correct:
until a beta has actually been published it has nothing to update to and sits on its current
build. The agent logs which channel it is on and which manifest it is reading whenever the hub
changes it, so `companion.log` is the place to confirm what that machine thinks it is following.
