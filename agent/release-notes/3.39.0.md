Every PC now tells the hub how it is secured. That fills a new **Security posture** card on the machine page, a matching table in the device sheet's Security section, and a fleet table on the Reports page -- each check labelled with the CIS Controls safeguard it is evidence for. This release also carries the BitLocker fix that missed 3.38.0.

This is a minor rather than a patch because it adds something the hub reads. Nothing on the console changes on its own the moment this arrives; a PC's posture card appears within about an hour of it updating.

**Deploy the hub first, as always.** This needs hub 1.134.0. An agent on 3.39.0 talking to an older hub sends its posture and the hub ignores it -- harmless, and it is sent again once the hub understands it.

## Security posture

The question this answers is the one an audit asks: is every PC running antivirus, is the firewall on, does the screen lock, who is a local administrator. Each PC now reads, once an hour:

- **Antivirus** as Windows Security Center lists it (Kaspersky, Defender or anything else registered), plus Defender's own status, which is all a Windows Server has. Signature freshness comes from the same place.
- **The firewall** for the domain, private and public profiles, as actually in force -- a Group Policy that switches a profile off is reported as off.
- **AutoRun and AutoPlay** policy, the **idle lock** (a machine-wide inactivity limit, or each signed-in user's locking screen saver), the **built-in Administrator and Guest** accounts, the members of the local **Administrators** group, **Secure Boot** and the **TPM**.

**The hub decides what passes, not the PC.** The agent sends the facts -- nine days, 1800 seconds, a list of names -- and the hub judges them against three settings under Settings -> Endpoint Security: how old signatures may be (7 days), the longest idle time before the screen locks (15 minutes, the CIS figure), and which extra accounts or groups may be local administrators. Changing a threshold takes effect straight away, with no agent release.

**Expect findings on the first day.** The built-in Administrator, Domain Admins and Entra role groups are always accepted as administrators; a helpdesk's own support group is reported until somebody adds it to the allow list. That is deliberate: this product does not get to decide who is trusted on your network. An enabled built-in Administrator is reported too, even where LAPS manages its password -- FleetHub cannot see LAPS.

**Unknown is not failed.** A check the PC could not read shows grey, not red, with the reason. Nothing here changes a machine -- switching a firewall on is still a script you run on purpose.

## A PC with BitLocker no longer drops offline after one missed heartbeat

**This fix was described in some copies of the 3.38.0 notes, but it did not ship in 3.38.0.** It was finished minutes after that release was cut, and reaches the fleet with this one.

Since 3.37.0, a PC that had a BitLocker report waiting to send could go offline on the console for up to an hour after a single failed heartbeat -- a network blip, or the hub restarting for an update. Commands still ran, but every heartbeat retry failed before it reached the network, and the only trace was "Heartbeat tick failed" in the agent's log. It recovered on its own at the next hourly BitLocker scan. That is fixed.

**If you saw PCs go offline for about an hour right after a hub update**, this is the likely cause. A PC has a BitLocker report waiting just after the agent starts and whenever its encryption state changes, so those are the moments it was exposed.

The same release also stops a BitLocker change that happened while a heartbeat was in flight from being marked as sent without reaching the hub. The encryption card could show the old state until something else changed on that PC.

## The usual

**What you need to do: nothing.** It arrives the way every agent update does, within about fifteen minutes.

**Installing an agent update restarts the service**, which drops any remote session or terminal open at that moment. Reconnect and it behaves normally.

**If it misbehaves.** Check the version on the machine page: it should read 3.39.0. A PC with no Security posture card an hour after updating has, on hub 1.134.0 or later, sent no posture: either its reports are not reaching the hub or the read failed as a whole, which this release does not log, so report the machine name. On an older hub no PC shows the card at all, because the hub ignores the posture -- update the hub first. A card where one check is grey with an error names the Windows component that refused, and that error is what to report. This is the first release to read these settings on machines other than the one it was built on.

**Which hub you need.** Hub 1.134.0 or later. The ordinary rule applies: hub first, then let the agent arrive on its own.
