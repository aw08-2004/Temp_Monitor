One fix, and it is the one that makes 0.2.0's headline feature work at all: **a device
provisioned by QR code now actually receives the hub URL and the enrollment secret from that
code.** On 0.2.0 it did not, and the failure was invisible from the device.

**Every device provisioned by QR with 0.2.0 needs attention.** They cannot pick this release up
on their own, and the reason is the fault itself: an affected device is pointed at a hub address
that does not exist, so it never reaches the hub, so it is never offered an update. See below.

# What was wrong

The hub puts the hub URL and the enrollment secret inside the provisioning code. That is the
whole point of provisioning by QR: nobody types a fleet-wide credential into a handset.

The agent never read them. It looked in the place an external management platform would put
them, and on a fully managed device this agent is that platform, so nothing was there. The
values arrived with the code, were handed to the agent, and were dropped.

**What made this expensive is that everything else worked.** Provisioning completed. The device
became a genuine device owner. The service started, posted its notification, and sat there
reporting to the placeholder address the app was built with. From the front the device looked
finished and correct, and the only visible symptom was that it never appeared in the console --
a symptom that also describes a phone with no signal, a wrong secret, and a hub that is down.

The one place it showed was the agent's own status screen, which names the hub it is actually
using. On an affected device that line reads as an obvious placeholder rather than as your hub.

# What to do

**A device already provisioned with 0.2.0 will not fix itself.** Two ways forward, and the first
is better if the device has nothing on it yet:

- **Factory reset and provision again** with a code minted from the hub. This is the clean path
  and it is what the flow is meant to be. The device comes back configured, enrolled and
  reporting.
- **Or install this release by hand and configure it on the setup screen.** The device stays a
  device owner, so nothing about its management is lost. Open the app, enter the hub URL and the
  enrollment secret, and it enrolls within thirty seconds.

**Devices installed by MDM push were never affected.** Managed configuration is the path the
agent was already reading correctly, so a device that got its settings from a policy has been
working the whole time.

**Check the status screen before you walk away from a device.** It names the hub the agent is
using, whether the device is genuinely a device owner, and whether a secret is present. Those
three lines are the difference between a device that is finished and one that only looks it.

# The usual

**Nothing else changed.** No new features, no behaviour changes anywhere else, and the signing
certificate is unchanged, so every provisioning code already printed stays valid.

**Once a device is on 0.2.1 it updates itself** like the other two agents, silently, on a fully
managed device.

**If a device still does not appear**, the agent logs to logcat under the tag `FleetHubAgent`:

```bash
adb logcat -s FleetHubAgent:*
```

It now says which hub URL it adopted from the code, and whether it took a secret from it. It
does not log the secret itself. Past that point, an enrollment the hub refused and one that
never reached the hub are logged as different things, which is the fork worth knowing before you
start checking the secret.
