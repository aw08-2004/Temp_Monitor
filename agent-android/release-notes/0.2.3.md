One fix, and it is the one that stops every Android device enrolling. **On 0.2.1 and on the
0.2.2 beta no device could enroll -- not by QR code and not by typing the hub URL and secret on
the setup screen.** Nothing you did wrong caused it, and nothing on the hub needs changing.

**Every device running 0.2.1 or 0.2.2 needs to be touched by hand.** It cannot update itself out
of this, for the same underlying reason it cannot enroll. See *What to do*.

As before, this agent is on its own 0.x version line; it is not behind the Windows agent's 3.x.

# What was wrong

The released app is shrunk at build time to keep the download small, because every managed phone
downloads it on every release. That shrinking also switched off the way the agent turned its own
data into text and back. On a developer's machine that switch is on, so every test passed; on a
phone it was off, and four things failed silently:

- **It could not save its enrollment.** The hub accepted the device and handed it its credential;
  the agent could not write that credential down, and by design an agent refuses to run on a
  credential it has not saved. So it threw it away and asked again thirty seconds later. Forever.
  The setup screen said *not enrolled yet, retrying every 30 seconds*, which was true.
- **It sent no telemetry** on 0.2.1, so the device never appeared in the console at all. The
  0.2.2 beta fixed this part only, which is why a 0.2.2 device shows up in the console and still
  never enrolls.
- **It could not read a command**, had it ever enrolled.
- **It could not read its own update manifest**, which is why it cannot update itself out of
  this.

It also stopped telling the hub which commands a phone can run. That one had no visible symptom.

# What to do

- **A device you are still setting up: factory reset and provision it again** with a QR code from
  the hub, **after uploading the 0.2.3 APK on the hub's provisioning page**. The signing
  certificate is unchanged, so codes you have already printed stay valid -- but they download
  whatever APK the hub is hosting, so the upload is the step that matters.
- **A device you would rather not wipe:** install 0.2.3 over the top by hand (`adb install -r`).
  It stays a device owner, keeps the hub URL and secret it was already given, and enrolls within
  thirty seconds.

**The hub has one entry per failed attempt.** Each thirty-second retry enrolled successfully on
the hub's side, so a device left running for a day has a few thousand unused agent records under
its name. They are harmless -- nothing holds their credentials -- and a device on 0.2.3 enrolls
once more and uses that one.

# Checking a device

The status screen is still the fastest check: it should say **Enrolled as** followed by an id,
within a minute of the device having a hub URL, a secret and a network. If it does not, the agent
logs to logcat under the tag `FleetHubAgent`:

```bash
adb logcat -s FleetHubAgent:*
```

A line reading *Enrolled as … but could not store the identity* is this fault, and should never
appear on 0.2.3. A line reading *Enrollment rejected (403)* is a wrong secret.

# The usual

**Nothing else changed.** No new features, no new data collected, and the signing certificate is
the same, so printed provisioning codes stay valid and 0.2.3 installs over 0.2.1 or 0.2.2 in place.

**Once a device is on 0.2.3 it updates itself** from then on, silently, on a fully managed device.
