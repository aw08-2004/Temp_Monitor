**Locating a phone works now. On every release before this one it never could.** If you have
pressed Locate on an Android device and been told *the location permission has not been granted
on this device*, that was not the device refusing you and not something anybody had switched
off -- the agent had simply never asked for the permission, on any device, ever.

Nothing on the hub changes and nothing needs reconfiguring. A device that updates itself to
0.3.0 is ready; a device somebody carries may need thirty seconds of a technician's time. See
*What you have to do*.

As before, this agent is on its own 0.x version line; it is not behind the Windows agent's 3.x.

# What the person holding the device sees

This is the release where locating starts working, so it is worth being exact about what that
means for whoever is carrying the phone. **None of it is new policy** -- it is the behaviour
locating was always specified to have, finally reachable.

- **Nothing is collected in the background, and there is still no location history.** A position
  is read only when an operator presses Locate, and the only record kept is of who asked and
  when.
- **The device says so, every time.** A notification naming the operator who asked appears
  before the position is read, and it appears whether or not a position is found. A locate is
  not something that can be done quietly.
- **On a fully managed device the permission is granted silently, by the agent itself**, the
  first time somebody locates it. Nobody at the device is asked, because a QR-provisioned phone
  has nobody in front of it. If that is not what you want for a particular fleet, the answer is
  not to grant `locate_device` to the people who would use it -- the capability is separate from
  the one that lets somebody restart a machine, specifically so that "may reboot a PC" never
  quietly means "may find out where an employee is".
- **On every other device somebody has to say yes**, in the ordinary Android permission dialog,
  on the agent's setup screen. Nothing grants it for them.
- **Approximate location is enough.** If somebody grants only approximate location, the device
  is still findable to about the nearest block, and the console shows the accuracy it actually
  had rather than implying more.

**The agent still does not ask for background location**, and that has not changed. It reaches
location with the screen off by briefly promoting its own foreground service for the length of
one request, rather than holding a standing right to follow the device around.

# What you have to do

- **A fully managed device: nothing.** It updates itself silently and grants itself the
  permission the first time anybody locates it.
- **Any other device needs two things by hand.** Install 0.3.0 over the top (`adb install -r`)
  -- a device that is not a device owner cannot update itself silently -- then open the FleetHub
  Agent app on it and press *Grant location*. The status screen now has a line telling you which
  state it is in, so you can see at a glance whether a device is findable before you need it
  to be.
- If somebody has already refused the permission twice, Android stops offering the dialog
  altogether. The button then takes you to the app's settings page, where the switch still is.

# Checking a device

The setup screen says one of two things, plainly:

- *Location granted -- this device can be located from the console.*
- *Location NOT granted. A locate from the console will answer "unavailable" instead of a
  position. Use the Grant location button below.*

From the console, a locate that still cannot answer now says what to do about it rather than
just reporting a refusal, and distinguishes a device waiting for somebody to grant it from a
fully managed device that would not grant itself -- the second means the phone was provisioned
without the right to grant sensor permissions, which is a provisioning problem rather than a
device somebody locked down.

The agent logs to logcat under the tag `FleetHubAgent`:

```bash
adb logcat -s FleetHubAgent:*
```

# The usual

**Nothing else changed.** No other new features, no other data collected, and the signing
certificate is the same, so printed provisioning codes stay valid and 0.3.0 installs over 0.2.3
in place.

**This has not yet been run on a real phone.** The permission work was written and reviewed
against the platform documentation, and the agent's own test suite covers what a workstation can
check, but no device has been watched granting the permission or returning a fix. Treat the
first device you update as the one that proves it.
