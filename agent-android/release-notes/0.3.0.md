**Locating a phone works now, and the console can ask the person holding a phone a question.**
Two things in one release. On every release before this one, locating a device never could work
and a message sent to a phone came back "not implemented by the Android agent".

**Locating.** If you have pressed Locate on an Android device and been told *the location
permission has not been granted on this device*, that was not the device refusing you and not
something anybody had switched off -- the agent had simply never asked for the permission, on
any device, ever.

**Messages.** `show_message` has been in the console and in the rules engine for a long time and
has always worked against a Windows PC. An Android device answered that it was not implemented,
which was true. It is implemented now, and nothing on the hub had to change for it -- see
*Messages to the person holding the device*.

Nothing on the hub changes and nothing needs reconfiguring. A device that updates itself to
0.3.0 is ready; a device somebody carries may need thirty seconds of a technician's time. See
*What you have to do*.

As before, this agent is on its own 0.x version line; it is not behind the Windows agent's 3.x.

# What the person holding the device sees (locating)

This is the release where locating starts working, so it is worth being exact about what that
means for whoever is carrying the phone. **None of it is new policy** -- it is the behaviour
locating was always specified to have, finally reachable.

- **Nothing is collected in the background, and there is still no location history.** A position
  is read only when an operator presses Locate, and the only record kept is of who asked and
  when.
- **The device says so, every time.** A notification naming the operator who asked appears
  before the position is read, and it appears whether or not a position is found. A locate is
  not something that can be done quietly.
- **On a fully managed device the permission is granted silently, by the agent itself**, the
  first time somebody locates it. Nobody at the device is asked, because a QR-provisioned phone
  has nobody in front of it. If that is not what you want for a particular fleet, the answer is
  not to grant `locate_device` to the people who would use it -- the capability is separate from
  the one that lets somebody restart a machine, specifically so that "may reboot a PC" never
  quietly means "may find out where an employee is".
- **On every other device somebody has to say yes**, in the ordinary Android permission dialog,
  on the agent's setup screen. Nothing grants it for them.
- **Approximate location is enough.** If somebody grants only approximate location, the device
  is still findable to about the nearest block, and the console shows the accuracy it actually
  had rather than implying more.

**The agent still does not ask for background location**, and that has not changed. It reaches
location with the screen off by briefly promoting its own foreground service for the length of
one request, rather than holding a standing right to follow the device around.

# Messages to the person holding the device

**A notice sent from the console now reaches a phone, and the person can answer it.** This is
the one thing a phone does better than a PC: a notice on a desktop waits for somebody to come
back to their desk, and the same notice on the phone in their pocket gets answered in a
corridor. It works from the rules engine exactly as it does for a Windows PC -- the same
message, the same buttons, and the same follow-up actions hanging off the answer.

What the person sees is a notification, not a dialog box. It arrives as a banner across the top
of the screen with the buttons you chose on it, and it stays in the notification shade until
they answer. That is deliberate rather than a limitation: Android does not let a background app
put a window on somebody's screen, and the ways round that are restricted to phone-call and
alarm apps, so a dialog would work on some phones and silently not on others.

Four things are worth knowing before you send one:

- **Swiping the notice away counts as an answer.** It comes back as *dismissed*, the same
  outcome as somebody closing the dialog on a PC, and any rule branch you hung off *dismissed*
  fires. It is not left sitting there unanswerable.
- **Three buttons is the maximum.** Android draws no more than three. A message with four comes
  back as a failure naming the limit, rather than showing three and quietly hiding the fourth
  answer nobody could then give. Every preset in the console fits.
- **A message with no timeout gets one hour.** On Windows a message with no timeout waits
  indefinitely. On a phone that would tie up one of the device's command slots, so the agent
  bounds it. Set a timeout if you want something other than an hour; the console's range is
  unchanged.
- **If notifications are switched off for the agent, the message comes back *no session*.**
  That is the same answer a PC gives when nobody is signed in, and it is reported as a message
  that ran and could not be shown rather than as a broken agent -- so a "then ask again later"
  rule branch still works. The result says which switch it was.

Button words are English on the device. If you type your own label in the console it is used
exactly as you typed it, in whatever language you typed it; only the built-in presets (OK,
Yes / No, Later and so on) fall back to English.

Nothing about this collects anything. It shows a notice and reports which button was pressed.

# What you have to do

- **A fully managed device: nothing.** It updates itself silently and grants itself the
  permission the first time anybody locates it.
- **Messages need nothing at all**, on any device, beyond the update itself -- no permission and
  no setup screen. The one thing worth checking is that notifications are not switched off for
  the agent, which the update does not change either way.
- **Any other device needs two things by hand.** Install 0.3.0 over the top (`adb install -r`)
  -- a device that is not a device owner cannot update itself silently -- then open the FleetHub
  Agent app on it and press *Grant location*. The status screen now has a line telling you which
  state it is in, so you can see at a glance whether a device is findable before you need it
  to be.
- If somebody has already refused the permission twice, Android stops offering the dialog
  altogether. The button then takes you to the app's settings page, where the switch still is.

# Checking a device

The setup screen says one of two things, plainly:

- *Location granted -- this device can be located from the console.*
- *Location NOT granted. A locate from the console will answer "unavailable" instead of a
  position. Use the Grant location button below.*

From the console, a locate that still cannot answer now says what to do about it rather than
just reporting a refusal, and distinguishes a device waiting for somebody to grant it from a
fully managed device that would not grant itself -- the second means the phone was provisioned
without the right to grant sensor permissions, which is a provisioning problem rather than a
device somebody locked down.

The agent logs to logcat under the tag `FleetHubAgent`:

```bash
adb logcat -s FleetHubAgent:*
```

# The usual

**Nothing else changed.** No other new features, no other data collected, and the signing
certificate is the same, so printed provisioning codes stay valid and 0.3.0 installs over 0.2.3
in place. One internal number did move: the agent now runs up to four commands at once instead
of two, because a message waiting on an answer occupies a slot for as long as the person takes
and two of those would have left a device accepting nothing else.

**Neither half of this has been run on a real phone.** Both were written and reviewed against
the platform documentation and type-checked against Android's own reference assembly, and the
agent's test suite covers what a workstation can check -- but no device has been watched
granting the location permission, returning a fix, or showing a message and reporting which
button somebody pressed. Treat the first device you update as the one that proves it.
